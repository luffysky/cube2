**驗證**：
- token：`alg=EdDSA`，`kid` 必填，只用 `https://identity.snowrealm.pet/.well-known/admin-jwks.json`。快取 10 分鐘；未知 `kid` 每分鐘重抓一次；同 `kid` 兩把鑰匙時拒絕。
- 聲明：
  - `iss` 必須正好是 `https://identity.snowrealm.pet`
  - `aud` 含 `snowrealm:brickduel:admin`
  - `scope` 要有完整的 `brickduel:admin:read`
  - `sub` 在 `BRICKDUEL_ADMIN_SUBJECTS` 裡（預定 `svc:snowrealm-games-admin`）
  - `iat`、`nbf`、`exp` 都是整數秒，時鐘容差 60 秒，`0 < exp−iat ≤ 600`
  - `jti` 必填，唯讀時可以重複使用
- 錯誤碼：405（不是 GET）→ 503 `disabled`（未設定）→ 401（不說明原因）／403 → 404 → 400／429（同一 `sub` 每分鐘超過 60 次）。JWKS 或資料庫不通時回 503 `unavailable`，後台要顯示「來源不可用」，不要當成 0。
- 回應：不送 CORS 標頭；全部 `Cache-Control: no-store`。
- 稽核：驗證通過的呼叫寫入 `zz.admin_log(at, sub, jti, path, status)`，不存 token、查詢字串或 IP。

**欄位補充**（跟 v0.2 一致，以下是 cube2 這邊的定義）：
- 等待刪除的存檔不會出現在任何列表或計數，單查回 404。
- `draws` 每筆多一個 `kind` 欄位（`box`／`wheel`／`slot`）。`summary` 只統計寶箱，範圍是 `from` 起（含）到 `to` 為止（不含），每個等級給 `count`、`share`、`published`（0–1）。
- `metrics`：
  - `players.linked` 目前是 0（`zz.identity` 為空）。
  - 下列欄位為 `null`：`steam`、`minorDeclared`、`regions`、`devices.unsaved`。
  - `subs.paid` 是 0，因為目前全部是體驗會員。
  - 另外多兩個欄位：`day`（UTC 日期）、`generatedAt`。
- `metrics/daily`：沒帶參數時回最近 7 天，最多 366 天。`coinsEarned`／`coinsSpent` 不含新存檔的起始金幣。`newSubs` 和兩個 `steam*` 欄位為 `null`。

**證據**：

## Issue #4：《轉磚》OAuth BFF（登入）

**契約**：照 cube1 `IDENTITY_P0_PRODUCTION_VERIFICATION_zh-TW.md` 的「Brickduel 整合契約」和 `dist/sso-flow.mjs`。細節見 cube2 `docs/BRICKDUEL_IDENTITY_ADAPTER_SPEC.md` §7。

| 端點 | 說明 |
|---|---|
| `POST /api/auth/start` `{intent: link\|recover\|restore}` | 只接受同站請求，`link` 要帶裝置金鑰。回傳 Games 入口網址並設定 `__Host-zzauth` cookie（Secure、HttpOnly、SameSite=Lax、10 分鐘） |
| `GET /api/auth/callback` | 唯一 callback：`https://brickduel.snowrealm.pet/api/auth/callback` |
| `POST /api/auth/result` | 同一個瀏覽器讀一次結果，讀完清除 |

- **入口網址**：`https://games.snowrealm.pet/?sso=brickduel&client_id=brickduel-bff&redirect_uri=<callback>&response_type=code&code_challenge=<S256>&code_challenge_method=S256&state=<43字>&nonce=<43字>`
- **伺服器端狀態**：
  - session id 只存雜湊。
  - verifier、state、nonce 用從 session id 衍生的金鑰（AES-256-GCM）加密保存。
  - callback 一進來就用一條 SQL 把這筆狀態標成已使用。
- **換 token**：`POST https://identity.snowrealm.pet/oauth/token`
  - 標頭帶 `x-snowrealm-client-secret`
  - body：`{clientId, redirectUri, code, codeVerifier, state, nonce}`
  - 5 秒逾時，不跟隨轉址
- **驗證 token**：
  - EdDSA／`kid`／`iss`
  - `aud=snowrealm:brickduel:api`、`scope=brickduel:account:link`
  - `sub`（UUID）、`iat`／`nbf`／`exp`（≤600 秒）、`jti`
  - token 若帶 `nonce`，必須跟伺服器存的一致
- **撤銷**：`POST /v1/token/status`，帶 Bearer token 和 client secret。只有 `200` 加上 `active === true` 才往下走：
  - `active:false`、401、403 → 結果 `revoked`
  - 503、逾時、JWKS 抓不到 → 結果 `unavailable`
- **綁定**：沿用現有的 `idLink`／`idRecover`：
  - 一對一，`jti` 只能用一次
  - 衝突回 409，兩份存檔、金幣都不動
  - 綁定時換發新的裝置金鑰，舊金鑰和引繼碼作廢
  - 存檔若在等待刪除，30 天內可用 `restore` 取消刪除
  - 匿名模式不受影響
- **回到遊戲**：`303 /?auth=<結果字>`，網址上沒有 token 或 code。可能的結果字：`linked recovered conflict pending none ban purged session expired replay state denied code token revoked unavailable off`。
- **環境變數**：
  - 沿用：`IDENTITY_ISSUER`、`IDENTITY_JWKS_URL`、`IDENTITY_AUDIENCE`、`IDENTITY_LINK_ENABLED`
  - 新增：`IDENTITY_BRICKDUEL_CLIENT_SECRET`（至少 32 字）
  - 可覆寫：`IDENTITY_AUTHORIZE_URL`、`IDENTITY_TOKEN_URL`、`IDENTITY_STATUS_URL`（必須是 https）

**證據**：
- `test/bff.test.js` 66 項全過（用測試自己產生的金鑰模擬 Identity），涵蓋：
  - 正常綁定
  - 錯 state、錯 nonce（token 端拒絕，或 token 內的 nonce 不同）
  - 重放、已用過的 code、過期
  - 換機：沒有 cookie、或拿別人的 cookie
  - 409：兩份存檔與金幣都不變
  - 已綁定的存檔不能再綁第二個帳號
  - 撤銷：5 種狀況
  - token 端 503／逾時、JWKS 失聯
  - 以上拒絕的情況都沒有發出裝置金鑰
  - 換裝置找回存檔、取消等待中的刪除、限流
- 瀏覽器測試 `test/authui.js` 9 項全過：
  - 功能關著時不顯示按鈕
  - 開著時導向入口網址，cookie 是 HttpOnly／Secure／Lax
  - localStorage 裡沒有任何相關資料
  - 回來後網址立刻清掉
- 正式站（`IDENTITY_LINK_ENABLED` 關著）：
  - `GET /api/auth/start` 回 405
  - `GET /api/auth/callback?code=x&state=y` 回 303 → `/?auth=off`
  - `/api/health` 的 `link` 為 `false`

**沒有正式 E2E**：cube1 的 `/oauth/authorize`、`/oauth/token` 目前回 503，`identity.snowrealm.pet` 也沒有正式部署證據。cube2 **不會**開 `IDENTITY_LINK_ENABLED`，要等兩邊用兩個測試帳號完成驗收。
