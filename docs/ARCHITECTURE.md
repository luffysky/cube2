# 架構與交接說明

給接手的人（或另一個 AI）看的：東西在哪、怎麼改、怎麼驗證。

## 怎麼跑

```
node build.js                      # 把 src/ 組成根目錄的 index.html（順便產生 manifest.webmanifest、sw.js、robots.txt、sitemap.xml）
python3 -m http.server 8765        # 在專案根目錄開一個本機伺服器（音樂要走 http 才載得到）
```

打開 `http://127.0.0.1:8765/`。沒有打包工具，`build.js` 只是把檔案內容貼進 `src/index.template.html` 的記號位置。這樣跑是純前端，沒有雲端功能。

要連後端一起跑：

```
npm install
npm run dev                        # http://127.0.0.1:8770/，遊戲和 /api 同一個埠，資料庫是記憶體裡的 Postgres，每次啟動都是空的
```

## 外掛介面 `ZZ.App`

`ui.js` 只管核心，其他功能用下面這些掛進去（`modes.js`、`shop.js` 就是這樣寫的）：

| 掛點 | 用途 |
|---|---|
| `App.sheets[name] = () => html` | 新增一個面板 |
| `App.opened[name]`、`App.closed[name]` | 面板打開後、關掉後要做的事 |
| `App.acts[name] = (button) => …` | 處理 `data-do="name"` 的按鈕 |
| `App.clicks.push((dataset, button) => true/false)` | 處理其他 `data-*` 按鈕，處理了就回傳 true |
| `App.inputs.push((element) => true/false)` | 處理面板裡的輸入欄位 |
| `App.go[name]` | 主選單 `data-go="name"` 的按鈕 |
| `App.kinds[name]` | 新增一種玩法（開局課就是 `lesson`） |
| `App.taps.push((game, event) => …)` | 收到玩家自己那面牆的每個事件（連線同步靠這個） |
| `App.again[mode]` | 「再來一場」在各模式下怎麼重開 |
| `App.boot.push(fn)` | 啟動時要做的事 |

對戰只有一種 `kind: 'battle'`，用 `mode` 區分：`ai`（挑電腦）、`rank`（排位）、`ghost`（分身）、`net`（連線）。

## 等級與稱號

`meta.js` 的「level and titles」。等級跟排位分開：每一場（任何模式）都有經驗值，贏了多 15、分數另外最多加 15，永遠不會掉。Lv 1 到 2 要 60，之後每級多 20，上限 100（`LV_MAX`），升級發金幣 `30 + 5 × 等級`。

稱號在 `TITLES`：`lv` 是跟著等級來的，`on(m)` 是某一場達成就拿到，`tot(d)` 是累計數字到了就拿到，`sub` 是會員才有。拿到的存在 `data.titles`，戴著的是 `data.title`（空字串時顯示目前最高的等級稱號）。名字在 `i18n.js` 的 `tt.<id>` 和 `tt.<id>.d`。一切都跑在伺服器同一份程式上，改本機資料沒用；從裝置匯入舊進度時經驗值最多 5000、稱號不帶過去。

排行榜每列多了 `lv` 和 `t`（稱號 id），房間名單也會顯示。

排位的名稱在 `TIERS` 和 `modes.js` 的 `tier0`～`tier6`：地基、石牆、塔樓、城堡、要塞、天空城、通天塔。

## 寶箱

`meta.js` 的「treasure boxes」。每天免費開 5 個（會員 10 個），用不完半夜就沒了。先抽箱子等級（木 60%、鐵 28%、金 10%、寶石 2%），再抽裡面的東西（`BOX`）。道具是七種平均隨機；外觀從還沒有、價格在範圍內的裡面挑，全都有了就給金幣。

有雲端存檔時**只有伺服器會開箱**（`Meta.remote()` 為真時頁面不自己算，送出 `draw` 等伺服器的答案；`server/rules.js` 用作業系統的亂數）。每次開箱都寫進 `zz.draws`，可以拿來核對公布的機率。純靜態空間沒有伺服器，就在頁面上用 `Math.random` 開。

機率表在寶箱畫面的「看機率」，內容直接從 `BOX` 算出來，改數字畫面就跟著改。台灣的規定是付費的機會型商品要在官網首頁、登入頁或購買頁公布機率，並保存紀錄至少 180 天；現在是免費的，但已經照這個標準做。

## 常見修改

**加一句文字或一種語言**：改 `src/i18n.js`（或 `modes.js`、`shop.js` 開頭的 `L.add`）。每個 key 四個字串，順序是繁中、英、日、韓。簡中不用寫；如果兩岸用詞不同，在 `i18n.js` 的 `WORDS` 加一組對照。跑 `node test/i18n.test.js` 會檢查有沒有漏。

**加一種磚樣式**：在 `view.js` 的 `TILE_DRAW` 加一個畫法，在 `meta.js` 的 `CATALOG.tile` 加一筆，在 `shop.js` 加名稱 `c.tile.<id>`。牆面同理（`paintWall`、`CATALOG.bg`、`c.bg.<id>`）。主題是 `style.css` 最後面的 `:root[data-skin="…"]`，加上 `CATALOG.theme`、`shop.js` 的 `SWATCH` 和名稱。

**加一個道具**：`engine.js` 的 `ITEMS`、`view.js` 的 `ITEM_MARK`（圖示）、`ui.js` 的 `useItem` 和 `foeItem`（效果）、`i18n.js` 的 `i<n>` 和 `i<n>t`、`meta.js` 的 `ITEM_PRICE`。

**加一堂開局課**：在 `tools/find_opener.js` 的 `SPECS` 描述目標形狀，跑出結果後用 `tools/make_openers.js` 產生 `src/openers.js`，再到 `modes.js` 加課名 `o.<id>.n` 和說明 `o.<id>.t`。`node test/openers.test.js` 會用引擎把每一步走一遍。

**調數值**：金幣、價格、段位門檻都在 `meta.js`；攻擊表和得分表在 `engine.js` 開頭；電腦等級在 `bot.js` 的 `LEVELS`。

**電腦的難度**有三層。`LEVELS` 是七個等級，陣列裡的位置就是存檔和伺服器用的編號，所以新等級只能加在最後面；由易到難的順序另外寫在 `ORDER`。設定裡的「電腦難度」（`set.ai`，-2 到 2）透過 `Bot.eased` 把「對戰」裡每個等級一起調慢調粗心、或調快調精準，不影響排位賽。排位賽的對手由 `meta.js` 的 `botFor(段位分)` 決定：0 分是最簡單的「新手」，150 分「小工」，300 分起才是原本的五級，每 450 分一級。調完用 `node tools/try_levels.js` 看每個等級「兩分鐘會送幾行、會自己疊死幾次」（也可以丟一組還沒寫進去的數值給它試），`node test/sim.js` 則是更完整的單人與對打數據。

**加一個音效**：`python3 -I tools/add_clip.py <名字> <音檔> [保留幾秒] [淡出幾秒]` 會裁切、轉單聲道、調到固定音量，塞進 `src/sfxdata.js`；再到 `view.js` 的 `LIB` 加一行怎麼播。

**換網域**：`build.js` 的 `SITE`（或環境變數 `ZZ_SITE`）。它會寫進 canonical、分享預覽圖的網址、`robots.txt` 和 `sitemap.xml`。

**重畫圖示或重截預覽圖**：`python3 -I tools/make_icons.py`；`node tools/shots.js`（需要的字型怎麼裝寫在檔案開頭），之後再 `node build.js` 一次。

## 幾個設計決定

**分身怎麼對打**：錄影記的是每一塊的最後落點，不是按鍵。重放時玩家送過去的水泥墊在最底下，錄影裡的落點整體往上抬同樣的排數，所以牆面還是對得上。如果分身被打到錄影裡沒有的擊倒，牆面就對不上了，這時改由電腦照錄影的速度接手。細節在 `replay.js` 開頭的註解。

**連線怎麼同步**：兩邊各跑各的遊戲。每次牆面有變化就送一張牆面快照，另外轉送畫面特效需要的事件、攻擊行數、道具、最後的結算。收到的每個欄位都會檢查範圍，不直接信任。沒有裁判伺服器，所以擋不住改程式作弊，真人排位還沒做。

**連線的資料怎麼走**：正式站（有 API）走自己的中繼。開房的人向 `/api/room` 要一個五碼代碼，朋友用代碼入座；之後兩邊各自用一般的 HTTPS 請求，把要說的話投進對方的信箱、順便收自己的信，對戰中大約每秒三到九次（看網路來回多快）。因為只用到普通的網頁連線，4G、Wi-Fi、公司網路都連得上，不需要打洞也不需要 TURN。每則訊息有編號，伺服器同一個編號只收一次，對方回報「讀到第幾則」之後才刪，所以請求丟了重送不會漏也不會重複。牆面快照只保留最新的一張。

**WebSocket 快車道**：兩邊都進房之後，頁面會另外開一條 WebSocket 到 `/api/ws`（`server/ws.js`，Vercel Functions 原生支援），之後每一輪交換改走這條線，內容和 `POST /api/room { a: 'x' }` 一模一樣，只是不用每次重新發請求。每封信還是先寫進資料庫，所以這條線隨時可以斷：Vercel 的函式到時限（`vercel.json` 設 300 秒）就會切斷連線，這時頁面自動退回一般請求並重新連線，換到哪一台機器都沒差。唯一留在記憶體裡的是「誰連在這台機器上」：收信的人剛好也在這台，信就當場推給他（`{ p: [...] }`），不用等他下一輪來拿；頁面只在那是「下一封」時才收，其他照舊去信箱拿。網址加 `?ws=off` 這次不開 WebSocket。

**三、四個人一起打**：自己的中繼開的房間最多 4 人（`Net.SEATS`）。房主按「開始」時，房間鎖門，誰在就誰打：兩個人就是原本的一對一，程式走完全一樣的路；三、四個人時 `start` 會帶名單（`multi: { roster, names, teams }`），四個人可以開「2 對 2」，座位依序紅、藍、紅、藍。

- 每個人的牆面快照照舊廣播給所有人，快照裡多帶自己被擊倒幾次（`d`）。每個對手在本機有一面鏡像牆（`S.multi.foes[座位].g`），畫面上大的那面是「目標」，其他人是牆上方的名牌（倒地次數、牆的高度）。點名牌換目標，隊友不能當目標。
- 攻擊只送給目標（`send(m, 目標座位)`，中繼的 `to`）；特效只轉播目標那一面。三人以上不開道具。
- 勝負：倒地最少的人贏，一樣多比送出行數；2 對 2 用兩人加起來的數字。中途離開的人（說再見，或 15 秒沒消息）排最後，其他人繼續打；對手全走光就直接算贏。
- 結算：每個人時間到時廣播自己的數字，等大家的數字到齊（最多 4 秒）再算名次。「再來一場」要所有還在的人都按了，房主才會重開。
- PeerJS 和瀏覽器內測試通道只有一對一。

**隨機配對**：`POST /api/room { a: 'quick', key }`。佇列（`zz.queue`）裡有人在等，就把最早的那一間拿下來（同時好幾個人來問，也只會有一個人拿到，靠 `FOR UPDATE SKIP LOCKED`），坐進去；沒有人就自己開一間排進佇列等。等的人每 6 秒 `{ a: 'still' }` 說一聲還在，超過 25 秒沒說話的房間不會被配到。兩邊打過招呼後房主自動開打（2 分鐘、沒有道具）。等 20 秒（`Net.QUICK_WAIT`）都沒有真人，就收掉房間，改跟電腦打一場，等級照玩家的段位，名字前面標「電腦」，結算畫面可以再找一次真人。

**超過兩個人的房間**：`zz.rooms.ks` 依座位順序放每個座位鑰匙的雜湊（房主是第一個），`cap` 是座位數（2 到 4）。信件表 `zz.post` 多了寄件座位 `src`，每個寄件人各自編號，收件人對每個寄件人各自回報「讀到第幾封」（`acks`）。信可以指定收件座位（`to`），不指定就是給房裡其他所有人。房主送 `{ a: 'lock' }` 之後不再收新人。舊版頁面（只有 `role` 和單一 `ack`）在兩人房照樣能用。

**房間的幾個邊角**：

- 房主把代碼傳出去的時候，人通常還在聊天 App 裡，遊戲頁面在背景是停住的。朋友這時候進房，會看到「進房了，等房主那邊回應」，最多等兩分半；房主一回到遊戲畫面就會馬上接上。等不到才會告訴朋友「請房主重開一個房間」。
- 離開的一方會留一句再見給對方（關掉分頁、離開頁面也會，用 `pagehide` 加 `keepalive` 送出最後一個請求）。房主離開時，沒有人的房間當場刪掉、代碼立刻失效；有客人的房間多留 15 秒讓對方收完最後的訊息。
- 一邊太久沒消息（對戰中 15 秒、大廳 70 秒）就當作斷線，同樣會留一句再見，免得對方回來看到一個假裝還活著的房間。
- 走中繼還是走 PeerJS，看的是「這個網址確定沒有 API」而不是「剛剛那次檢查有沒有成功」。頁面剛開時網路剛好不通，不會因此被分到 PeerJS 那邊去（那樣兩個朋友會各在一邊，永遠找不到對方的房間）；要開房時會再確認一次。

原本是用 PeerJS 的公用配對伺服器加 WebRTC 直連。實測那台公用伺服器不會把加入的請求轉給房主（房間明明開著，對方卻收到「找不到房間」），所以現在只有在沒有 API 的地方（純靜態空間）才退回那條路，而且不保證連得上。

中繼的代價是延遲和請求數：對手的畫面每秒更新三到九次，攻擊大約晚零點幾秒到；一場兩分鐘的對戰大約是幾百到一千多次函式呼叫。量大了以後可以改成「中繼只負責牽線，資料走 WebRTC 直連，直連不通才退回中繼」，`net.js` 裡中繼和直連用的是同一個介面（`on`、`send`、`close`），可以直接接上去。

**簡中為什麼用轉的**：少維護一份翻譯，新加的繁中文字自動有簡中。代價是用詞偶爾偏台灣，用 `WORDS` 補。

**規則的版本**：`engine.js` 的 `ZZ.RULES`。錄影會記下它是在哪一版規則下錄的，版本不同的錄影不會拿來當分身（落點會對不上）。改了會讓同樣的操作有不同結果的規則時，把它加一。

**為什麼是單一 HTML**：方便丟到任何靜態空間，也方便在預覽環境裡直接跑。

## 後端：雲端存檔與排行榜

### 整體

```
瀏覽器 ──HTTPS──▶ Vercel Functions（/api/health、/api/rpc、/api/board）──HTTPS──▶ Neon Postgres
```

瀏覽器從來不直接連資料庫。資料庫的連線字串只存在 Vercel 的環境變數裡（Neon 連結到專案時由 Vercel 自動寫入，名字是 `DATABASE_URL`），程式只讀 `process.env`，不會出現在程式庫、回應或紀錄檔裡。`server/db.js` 是唯一碰它的檔案。查詢用 Neon 的 HTTP 驅動，一次查詢一個請求，請求之間不留連線；所有值都用參數傳，沒有任何 SQL 是用玩家送來的字串拼出來的。

API 只給同一個網址的頁面用：不送任何 CORS 標頭，請求如果帶著別站的 `Origin` 就拒絕。身分用頁面自己保存的 bearer token，不用 cookie。

### 誰說了算

遊戲不等網路。玩家每做一件事（買東西、打完一場、領任務），`src/meta.js` 當場算好、畫面立刻更新，就跟純前端時一樣。差別是每個操作會同時經由 `Meta.onOp` 報給 `src/cloud.js`，排進佇列送到 `/api/rpc`。

伺服器（`server/rules.js`）載入**同一份** `src/meta.js`，在自己那份存檔上把操作重做一次（`Meta.run`），然後把結果整份回傳。前端收到後用它取代本機存檔，再把還沒送出去的操作疊上去重播。所以畫面上永遠是「伺服器確認過的，加上它還沒聽到的」，而伺服器的版本永遠算數。

結果是：改本機的金幣數字沒有用。買不起的東西、沒擁有的外觀、沒完成的任務，在伺服器那邊就是失敗，下次同步時本機會被改回來。

操作的種類（都在 `meta.js` 最下面的 `RUN`）：`fin` 對局結算、`buy` `set` `item` 購買、`wear` `wset` 穿戴、`bring` `take` 帶道具、`login` `job` 簽到與任務、`first` 首次通關、`name`、`sub` `unsub`、`note`。每個參數進來都先檢查型別和範圍。

同步的細節：

- 每個操作有一個隨機 id，伺服器記得最近 160 個。回應在半路丟了，前端重送同一批，不會重複生效。
- 存檔有版本號，寫入時用「版本沒變才寫」。兩台裝置同時存，後到的那個會重讀再做一次，兩邊的操作都會算進去。
- 離線時操作留在 `localStorage`，重新開頁面也還在，連上後依序補送。
- 同一個瀏覽器開好幾個分頁時，它們共用同一份儲存空間，所以只能有一個帳號：建帳號這一步用 Web Locks 排隊，排到的分頁會先看別的分頁是不是已經建好了，是的話直接沿用，自己還沒送出的操作照樣送到那個帳號（靠操作 id 去重，不會算兩次）。瀏覽器不支援排隊時，後建好的那一方會把自己多出來的帳號刪掉。另一個分頁換了存檔或刪了雲端資料，其他分頁透過 `storage` 事件跟著換（`Cloud.follow`）。
- 遊戲的「一天」和「一季」全球統一在台灣時間午夜換（`Meta.TZ`），前端的時鐘會跟著伺服器校正，不看裝置自己的時間。

### 對局結果

伺服器沒有親眼看到對局，但每場結果要附一卷「帶子」（`src/replay.js` 的 `Tape`）：玩家這一邊每一塊落在哪、有沒有用暫存、什麼時候吃到幾排水泥、什麼時候被擊倒。伺服器用同一份 `engine.js` 把帶子走一遍（`Replay.check`），檢查三件事：

1. **是不是一場可能的對局**：每一塊都要是那個種子會發的那一塊（含暫存），落點要放得下、底下有東西撐著；宣稱的「轉」要符合地形（T 看四個角，其他方塊要卡死不能動）。
2. **數字對不對得上**：行數、各種轉的次數、四消、連擊要跟帶子走出來的一模一樣；送出行數和分數不能超過帶子走得出來的量（分數另外容許落下加分和擊倒對手的加分）。自己被擊倒幾次以帶子為準。
3. **不能重複交**：同一個種子的帶子每個帳號只收一次（記最近 80 場）。

排位賽和 40 行競速沒有對得上的帶子就**整場不算**（回 `proof`）；其他對戰照舊給金幣，但只有對得上帶子的分數才會上「單場最高分」榜。有道具的對戰不錄帶子（道具效果跟對手有關），所以不上榜。

再加上原本就有的兩層：`Meta.cleanMatch` 的合理範圍，和**時間額度**（每個帳號可回報的對局時間隨真實時間以 1.5 倍累積，上限 8 小時；每回報一場扣掉那場的長度，至少 20 秒）。

擋得住的：改數字、灌分、拿同一場重複交、憑空宣稱每一塊都是 T 轉。擋不住的：帶子看不到對手那一邊，所以「擊倒對手幾次」只能限制在時間內辦得到的範圍；以及有人真的寫一個會玩的程式來玩（那等於外掛，要靠行為偵測）。`zz.players.ban` 設成 `true` 可以讓一個玩家從所有排行榜消失。

改了規則（會讓同樣的落點有不同結果）要把 `ZZ.RULES` 加一，舊頁面送來的帶子就會對不上而被拒絕，玩家重新整理後恢復正常。

### 帳號

沒有信箱、沒有密碼。裝置第一次有「操作」時（不是一打開頁面就建，避免爬蟲和路過的人各佔一筆）呼叫 `hello`，伺服器產生一個隨機 id 和一個隨機密鑰回給裝置，資料庫只存密鑰的 SHA-256。就算資料庫整份外流，也沒辦法拿來登入。

建帳號時，裝置上原本的進度會帶上來一次（玩家可能在有雲端之前就玩過）。因為那份資料來自誰都改得了的瀏覽器儲存空間，`rules.importState` 會夾到合理範圍：金幣最多 20000、段位分最多 900、每種道具最多 20 個、只認商店裡真的有而且買得到的外觀。匯入的最高分和段位**不會**進排行榜，排行榜只收伺服器親眼看到的對局。

換裝置用引繼碼：8 碼、10 分鐘內有效、只能用一次，資料庫同樣只存雜湊。輸入後會先顯示那是誰的存檔，確認才切換。一個帳號最多 5 台裝置，超過時最舊的那台會被登出。同一個位址十分鐘內只能試 12 次碼，一天只能建 40 個帳號；位址只以加了密鑰的雜湊形式存在計數表裡，過期後（最久兩天）清掉。

### 端點

| 端點 | 說明 |
|---|---|
| `GET /api/health` | 這裡有沒有 API、有沒有連結資料庫。前端靠它決定要不要開雲端功能。加 `?deep=1` 會實際查一次資料庫並回報來回時間 |
| `POST /api/room` | `{ a: 'open' \| 'join' \| 'x' \| 'close', … }`。連線對戰的房間：開房、入座、交換訊息、關房。座位用頁面自己產生的隨機鑰匙認，資料庫只存雜湊。房主最後一次交換訊息帶 `end: true`，伺服器就順手把房間收掉 |
| `POST /api/rpc` | `{ a: 'hello' \| 'sync' \| 'code' \| 'redeem' \| 'delete', … }`。除了 `hello` 和 `redeem` 都要 `Authorization: Bearer <id>.<密鑰>` |
| `GET /api/board?b=rp\|score\|sprint` | 排行榜前 50 名。`&s=all` 看歷來（段位榜只有本季），`&me=<代號>` 順便回自己的名次。回應可以在 CDN 快取 30 秒 |

錯誤一律是 `{ ok: false, why: '代碼' }`，不帶任何內部訊息。

### 資料表

都在自己的 schema `zz` 裡，不會跟同一個資料庫的其他東西衝突。第一次有請求發現表不存在時自動建立（`server/db.js` 的 `SCHEMA`），之後要加欄位就在那個清單後面加 `ALTER TABLE … ADD COLUMN IF NOT EXISTS`。

| 表 | 內容 |
|---|---|
| `zz.players` | 一個玩家一列：`state`（整份存檔，jsonb）、`srv`（伺服器自己的筆記：最近的操作 id、時間額度）、版本號、排行榜要用的 `rp` `season` `rg`、`pub`（排行榜上的公開代號）、`ban` |
| `zz.keys` | 裝置密鑰的雜湊 → 玩家 |
| `zz.codes` | 引繼碼的雜湊 → 玩家，附到期時間 |
| `zz.scores` | 最高分與 40 行競速的最佳成績，每個玩家每個榜每季一列，另有一列「歷來」。競速存負的毫秒數，這樣所有榜都是「越大越好」 |
| `zz.rate` | 限流計數 |
| `zz.rooms` | 連線對戰的房間：代碼、每個座位鑰匙的雜湊（`ks`）、座位數（`cap`）、到期時間（三小時）。`hk`、`jk` 是舊欄位 |
| `zz.post` | 房間裡每個座位的信箱，記著是哪個座位寄的。收件人讀過就刪，房間到期或關閉時整批清掉（取代舊的 `zz.mail`） |

玩家按「刪除雲端資料」時走 30 天狀態機（Owner C-022，規格見 cube1 `docs/BRICKDUEL_ACCOUNT_LINK_AND_DELETION_POLICY_zh-TW.md`）：
- **有效 → 等待刪除**：`delete` 在 `zz.players.gone` 記下伺服器時間（重複申請以第一次為準），回傳 `until = gone + 30 天`。等待期間存檔不能被讀寫、結算或產生引繼碼（API 回 409 `pending` 附 `until`），也從所有排行榜消失；裝置密鑰與 `zz.identity` 綁定都**保留**，不在當天級聯刪除。
- **等待刪除 → 有效**：同一份存檔的任何裝置用自己的密鑰呼叫 `restore`，或已綁定的 SnowRealm 帳號 `idRecover` 帶 `back: true`，在期限內取消刪除（`restored` 記下時間）。公開代碼、引繼碼都不能取回。期滿後回 410 `purged`。
- **等待刪除 → 刪除**：`hello()` 與 `delete` 會順帶執行清理：單一 SQL `DELETE … WHERE gone < now − 30 天`，與取消刪除以列鎖互斥、可重複執行；密鑰、成績、對局、流水帳、綁定紀錄由外鍵跟著刪。每次真的刪到東西，在 `zz.purges` 留 `(時間, 份數)`，不含玩家資料。
- 換裝置後沒有任何裝置能再打開的舊存檔，也同樣進入 30 天等待。
- 用戶端：申請後記下 `del = {id, key, until}`，畫面顯示當地時間的確切截止時間、「取消刪除」與「不恢復，改開新的雲端存檔」；另一台裝置下次同步收到 409 `pending` 也會改成這個狀態。

### 部署

Vercel 專案連到這個 GitHub 程式庫，推到 `main` 就部署正式站，推到其他分支會有預覽網址。需要的設定只有一個：在 Vercel 的 Storage 把 Neon 資料庫連到專案（會自動產生 `DATABASE_URL`）。沒有這個變數時 API 會回報 `db: false`，遊戲自動退回純本機模式。

`/api/health?deep=1` 會顯示函式跑在哪一區（`region`）和查一次資料庫要多久（`ms`）。如果函式和資料庫不在同一區，每次查詢都會慢，可以在 `vercel.json` 用 `"regions"` 把函式搬到資料庫旁邊。

想多一層保護，可以在 Vercel 的 Firewall 對 `/api/` 加每個位址的請求頻率限制。

`.vercelignore` 把文件、測試和工具排除在外，它們不會出現在網站上（API 需要的 `api/`、`server/`、`src/` 都還在）。`vercel.json` 的 `headers` 幫音樂和圖示加了快取時間，並且請搜尋引擎不要收錄原始碼。

### 頁面能跑哪些程式（CSP）

`build.js` 每次組好頁面，會算出頁面裡每一段程式的雜湊，寫成 `Content-Security-Policy` 放進 `vercel.json`：瀏覽器只執行這幾段和同網址的檔案，其他一律不跑。所以**改完 `src/` 一定要重新 build，連同 `vercel.json` 一起提交**，不然新的頁面會被自己的規則擋住（CI 會檢查）。本機的 `tools/dev-server.js` 送出同一份規則，瀏覽器測試就是在這份規則底下跑的；網址加 `?csp=off` 這次不送。

### 名字

`Meta.cleanName` 會把辱罵字眼和冒充官方的名字清空（清單在 `meta.js` 的 `BAD_NAME`，故意保持很短），伺服器用的是同一份。玩家看得到的說明在 `privacy.html`。

### 自動測試

`.github/workflows/test.yml`：推到 `main` 或開 PR 時，檢查提交的 `index.html` 和 `build.js` 產生的一致，再跑 `npm test`。另一個工作 `browser` 用執行環境內建的 Google Chrome 加 Playwright（裝在 `/opt/npm-tools`，不下載瀏覽器），由 `test/browser-run.js` 自己開兩個靜態伺服器（8790、8765），依序跑 18 個瀏覽器測試。本機也能 `node test/browser-run.js flow rwd` 只跑幾個。

## 安裝成 App、離線、被搜尋到

**Service worker**（`sw.js`）只做三件事：頁面本身永遠先向網路要，四秒內沒有回應或根本沒網路才用留存的那一份，所以新版不會被舊的快取卡住；音樂和圖示第一次抓到之後留著；`api/` 底下的請求完全不碰。每次 build 版本字串都會變，瀏覽器就會換上新的 worker 並清掉舊的頁面快取。網址加 `?sw=off` 這次不註冊。

**安裝**：Chrome、Edge、Android 會送 `beforeinstallprompt`，這時選單最下面出現「安裝成 App」；iPhone 沒有這個事件，改成說明怎麼用「分享 → 加入主畫面」，而且要等 service worker 註冊成功才顯示（頁面被放在別的地方、旁邊沒有 `sw.js` 時就沒有東西可以裝）。通訊軟體內建的瀏覽器、其他 App 裡開的網頁裝不了，就不顯示。

**給搜尋引擎的**：`<head>` 裡的標題、說明、canonical、五種語言的 hreflang、Open Graph、Twitter 卡片、JSON-LD（VideoGame）都由 `build.js` 從 `i18n.js` 的 `seo.*` 填進去。頁面裡的文字在 build 時先填好繁體中文，不跑程式的爬蟲也讀得到。`?lang=en` 這類網址會顯示該語言並把自己設為 canonical。文案裡刻意不用別人的商標名稱。

## 各種螢幕

版面分兩層。`style.css` 最後面的「各種螢幕」是斷點：≤359、480、600、768、1024、1440、1920、2560，加上橫拿的手機和橫拿的平板，管選單、面板、文字和按鍵。對局畫面的磚塊大小、兩側欄寬、平板的按鍵高度由 `ui.js` 的 `layout()` 依視窗算：手機最多 34 px 一格，平板和直立視窗到 56，橫向大螢幕到 64，側欄跟著磚塊放大。`node test/rwd.js` 會把十九種螢幕各截三張圖（`shots/rwd-*.png`）並檢查沒有東西跑出畫面。

## 200 種道具（engine.js ITEMS）

道具是一串「效果」。12 種效果：自己用的 chisel（拆底下 n 排）、shield（擋水泥 ms）、goldT / goldI（接下來 n 塊）、trowel（補洞）、boost（ms 內送出行數 ×x）、cleanse（清掉正要來的水泥）、score（加分）；打對手的 grout（灌 n 排）、freeze（ms 不能動）、curse（對手接下來 n 塊是 S/Z）、blind（ms 看不到下一塊）。

- 1–7 號是原本的七種，效果、價格、編號都不變（舊存檔、錄影、連線相容）。
- 8–52 號是單一效果的不同強度；53–200 號是兩種效果的組合（自己＋對手、自己＋自己、對手＋對手，同種不重複）。
- 強度算出稀有度 1–5 星和價格（30–115）。盤面出現機率 `ITEM_POOL`：前七種最常見，越強越少。
- 名稱與說明在 `i18n.js` 依效果自動產生（四種語言）；圖示用第一個效果的記號，組合在右下角加第二個效果的顏色。
- 使用：`ui.js` 的 `useItem` 依序執行效果；打對手的效果在連線時由對方頁面收到編號後執行（凍結、遮眼另外在自己畫面顯示）。
- 伺服器匯入本機存檔時每種最多 20 個、全部合計最多 80 個。

## 關卡模式（levels.js、levelmode.js）

- **1000 關**：`Levels.make(n, salt)` 只靠關卡編號產生地形（8 種：洞、直井、樓梯、雙洞、T 轉槽、Z 字、柱子、雙洞亂數）、目標（挖光水泥／消 N 行／做 N 次 T 轉）和方塊順序（遊戲用關卡的種子），每個人玩到的都一樣。地形最高 12 排。
- **電腦驗證**：`node tools/make_levels.js` 讓電腦（最強的電腦師傅，不失誤）把 1000 關全部打一遍，把每關用了幾塊（par）和用了哪個 salt 寫進 `levels.js` 的 PAR 表。打不完或少於 4 塊就換下一個 salt。改了產生規則一定要重跑（約 4 分鐘）。
- **星星**：par+2 塊內 3 顆，par×1.3+3 內 2 顆，其他 1 顆。上限 par×1.8+8 塊。
- **獎勵**：第一次過關 20 + 每 25 關多 5 金幣；每多一顆星 10 金幣。伺服器用同一套規則重算星星，擋跳關、擋超過上限，每關至少扣 5 秒（或每塊 0.33 秒）的遊玩時間額度。
- **無限挑戰**：隨機地形一關接一關，越後面越難，記最佳紀錄。
- **自訂關卡**：編輯器畫地形、選目標、設上限，做成 `?lv=代碼` 的連結分享（代碼是 base64url，最多 12 排）。
- **關卡任務**：每波 5 個任務是 3 個一般 + 2 個關卡任務。
- 測試：`test/stages.js`（瀏覽器，電腦代打一關到結算）、`test/luck.test.js`、`test/api.test.js`。

## 挑戰大自然（weather.js、wxmode.js）

- **天氣只在這個模式**：其他模式完全不受影響。`ZZ.Weather` 靠種子和遊玩時間決定天氣，同一個種子同一時間天氣一樣（之後連線對戰就靠這個共用一片天）。
- **五種天氣**：強風（落下的方塊被吹歪）、大雨（掉得快、鎖得快、落地後還會順著風滑）、下雪（掉得慢，但雪會一格一格積在牆上，不會自己填滿一排）、雷雨（風加雨，偶爾打雷把最上面一格變水泥）、濃霧（下面幾排看不到）。
- **節奏**：開場 6 秒晴天，之後每 20–30 秒變天，不會連續同一種；一分半後開始變強，最強 3 級。底速每秒變快一點。
- **雪**是新的格子種類 `ZZ.SNOW = 9`（白色雪塊），消行時跟一般方塊一樣消掉。
- **畫面**：盤面上疊一層 canvas 畫雨、雪、風、閃電和霧，純外觀；對遊戲的影響全在 weather.js。風速、雨量、積雪、能見度、幾秒後變天寫在「下一個」旁邊。
- **計分與獎勵**：遊戲分數 + 每撐 1 秒 5 分。天氣輪替的場次撐 20 秒以上才有金幣（每 20 秒 1 + 每 4 行 1，最多 60），記最佳紀錄、上「挑戰大自然」排行榜；只練一種天氣的不算獎勵。伺服器用遊玩時間額度擋「秒回報一小時的場次」。
- 測試：`test/weather.test.js`、`test/skies.js`（瀏覽器）、`test/api.test.js`。
- **天氣對戰**：對電腦、隨機配對（伺服器配對分兩個池：一般 `''`、天氣 `'wx'`，`zz.queue.pool`）、開房間時打開「天氣對戰」（只限兩人房）。開場由房主出一個天氣種子，兩邊頭上同一片天。消 4 行或 T 轉雙消以上，丟一種強烈天氣（3 級、9 秒）給對手（連線用 `{t:'w'}` 訊息）；電腦的牆只吃積雪和雷擊，電腦消 4 行也會丟回來。天氣對戰不錄影、不走錄影驗證。
- **天氣排位**（`lv.wxr`）：撐過 20 秒的天氣對戰才算；贏電腦 +15、贏真人 +25、平手 +5、輸 −10（最低 0）。op `wxb`，伺服器每場扣一場對戰的時間額度，記到「天氣排位」排行榜。
- **天氣資訊框**：有鍵盤時在「下一個」下面；觸控螢幕右欄要放暫存和暫停鍵，所以放在左欄暫存下面。

## 磚塊遊戲目錄（games/）

- `games/index.html` 是所有磚塊遊戲的目錄，轉磚主選單底下有「更多磚塊遊戲」連過去。每個小遊戲是 `games/<名字>/` 底下一頁 HTML 加一支 JS，共用 `games/games.css`（同一套磨石子地板、水泥牆、上釉磁磚的樣子）。
- 小遊戲的腳本是外部檔案（`script-src 'self'`），不用改網站的 CSP；service worker 也不碰 `games/`。
- **磚蛇**（`games/snake/`）：16×16 場地。吃到的磚接在頭後面，身上同色連 3 塊以上就消掉（蛇變短），消完合起來又連成 3 塊算連消，分數加倍。每吃 6 塊出現一塊水泥，偶爾出現金磚（幾秒後消失，+100）。越吃越快，難度分簡單／普通／困難（起始速度、最快速度、陷阱數量不同）。5 條命，撞牆、水泥、豎起的尖刺或自己少一條，蛇原長度在有空間的地方重生。吃到一定數量後出現陷阱：尖刺（輪流豎起，豎起前有黃色斜紋）和一對傳送門。每個難度各記最佳分數。最佳分數只存在這台裝置（`snowrealm.snake.best`），還沒接金幣和帳號。規則在 `Snake`，跟畫面分開，`test/snake.test.js` 直接測；`test/bricks.js` 是瀏覽器測試。
- **打磚塊**（`games/breakout/`）：場地 360×540（畫面等比縮放）。板子打到的位置決定反彈角度（最多偏 60°）。水泥磚兩下、鐵磚打不破（不算在過關裡）。約 14% 的磚帶道具：加寬、多球、變慢、愛心。5 條命，三種難度（球速）；每過一關快一點，有上限。規則 `Breakout`，`test/breakout.test.js` 有一整局自動玩到第 3 關。

- 小遊戲的說明框太長時在框內捲動（不顯示捲軸），放得下就置中。
- **金幣與帳號**：`games/rewards.js` 是三邊共用的規則（小遊戲頁、轉磚頁 `Meta.miniDone`、伺服器重算 op `mini`）。小遊戲結束時把結果放進瀏覽器佇列 `snowrealm.mini.queue`，打開轉磚時 `src/minis.js` 逐筆入帳；分數類照分數、時間類照難度（新紀錄 +5）、關卡類只付第一次過關和多拿的星。每 3 秒最多 1 枚、分數類單場最多 30、每天最多 300。紀錄存在 `Meta.data.mini`（雲端存檔一起同步），關卡類的星星換裝置也會帶到小遊戲的關卡列表。伺服器每筆扣遊玩時間額度（op 參數上限放寬到 5 個）。
- 排行榜：每款每個難度一個分數榜或時間榜（`m_<遊戲>_<0|1|2>`，時間存負數、顯示成時間），關卡遊戲比星星總數（`m_push`、`m_sort`、`m_picross`）；由伺服器重做 `mini` 操作時記分，分數超過遊玩時間每秒 1500 分就不上榜。轉磚排行榜的「小遊戲」分頁選遊戲和難度。

## 自動翻譯（C-024）

- 字典仍寫在各檔案的 `L.add({...})`。一條字可以只寫中文（字串，或缺後面幾欄的陣列），表示「交給機器翻」。
- `tools/dict.js`：讀出所有字典，算出缺哪些語言（`todo`），以及把機器翻譯補進空欄（`merged`）。人寫的欄位永遠優先；中文改過，舊的機器翻譯自動作廢、重翻。
- `tools/i18n-scan.js`：寫出 `i18n/todo.json`；`--check` 有待翻就失敗。
- `tools/i18n-auto.py`：預設用 Google Gemini（`GEMINI_API_KEY`，免費額度即可；只送遊戲介面文字），一次 40 條、要求回傳 JSON，`{0}` 空格與 `<標籤>` 不一致的就不收、留給人翻；結果寫進 `i18n/auto.json`（含原中文、模型、日期）。Argos Translate 留著當選項，但 Owner 決定不用（C-025，品質不足）。`--engine mark` 是測試用的假引擎。
- `.github/workflows/i18n.yml`：推到 main 而且動到字典時掃描；repo 有 `GEMINI_API_KEY` 這個 secret 才翻譯、重新建置、跑測試、commit 回 main（Vercel 接著部署）。沒有金鑰就只列出待翻清單。現階段由 Claude 直接寫好四種語言。
- `build.js`：把機器翻譯補進頁面（`ZZ.L.machine` 記哪些欄是機器翻的；設定頁在外語時會提示「有些文字是機器翻譯」），並輸出 `server/i18n-data.json`（每條字五種語言、來源 human／machine／hans／zh）。
- `server/words.js`：每個伺服器執行個體處理第一個 `/api/rpc` 時，版本不同就把 `server/i18n-data.json` 寫進 `zz.i18n`（`zz.i18nmeta` 記版本）。`src = 'admin'` 的列（後台人工改的）不會被覆蓋。
- 磚塊小遊戲：文字寫在 `src/games-dict.js`（同樣四欄），`build.js` 產生 `games/words.js`（五欄：繁、簡、英、日、韓）。`games/i18n.js` 依 `?lang=`、轉磚的語言設定、瀏覽器語言決定語言，填入 `data-t`（文字）、`data-ta`（aria-label）、`data-th`（含標記）、`data-tk`＋`data-tv`（含會變動的數字）；遊戲程式用 `SRW.t()`。
- 不在自動翻譯範圍：隱私政策、使用條款（依地區另寫，見 `legal/`）。

## 每種語言一個網址（C-027）

- `build.js` 從同一個模板產生五個主頁：`index.html`（繁中，網址 `/`）、`index.zh-Hans.html`、`index.en.html`、`index.ja.html`、`index.ko.html`。各自的 `<html lang>`、title、description、Open Graph／Twitter 文字、`og:locale`、canonical、JSON-LD（`inLanguage`、`url`）與首屏文字都換成該語言；script 完全相同，所以 CSP 雜湊共用。
- `vercel.json` 的 `rewrites` 把 `/zh-Hans`、`/en`、`/ja`、`/ko` 送到對應檔案（網址不變，相對路徑 `api/`、`games/` 照常）。`src/ui.js` 從網址路徑（或舊的 `?lang=`）決定語言，canonical 改成路徑形式。`sitemap.xml` 列出五個網址與互相的 hreflang。
- 小遊戲頁：建置時加上 canonical 與五語 hreflang（`?lang=`），`games/i18n.js` 依語言填 title、description 並更新 canonical。

## 地區法律文件（C-025，草稿）

- `legal/src/`：各語言的共同文字（`privacy|terms.<zh-Hant|en|ja|ko>.html`；日文、韓文直接依當地法寫）與 `regions.js`（12 個地區各自的補充、適用法律）。`tools/legal.js`（由 `build.js` 執行）產生 `legal/<地區>/privacy.html`、`terms.html`，每頁都標示「草稿、待律師審閱」並 `noindex`；中國大陸版由繁中轉簡體。根目錄的 `privacy.html`、`terms.html`（臺灣版＋英文）也由同一份文字重建，並列出其他地區。
- 遊戲裡的隱私政策、條款連結會依玩家在第一次進來時選的居住地區，改連到 `legal/<地區>/`（臺灣與尚未選擇者用根目錄版本）；小遊戲的側邊選單也一樣。
